# E3 — Recording Container Under Kinect Load

**Status: PASSED — MCAP confirmed as the take container, with one binding
design consequence: the recorder must use a custom `IWritable` (the stock
`FileWriter` aborts the process on disk-full instead of erroring).**

Run 2026-07-29. Spike: `spikes/e3-mcap-harness/` (disposable). MCAP C++
`releases/cpp/v2.1.3` (pinned via FetchContent), system zstd 1.5.7 /
lz4 1.10. Target volume: the actual takes directory
(`takes/` on `/home`, btrfs on NVMe — the real storage path). Payload:
**real depth frames from the E1 clip** (f32 mm → u16 0.1 mm, 901 frames
cycled) + incompressible 680 kB pseudo-JPEG at 30 Hz + 1 Hz JSON events —
matching E1's measured rates (~33.4 MB/s aggregate).

An earlier sweep run used synthetic per-pixel-noise depth generated inside
the timed loop; it showed 1.4× real-time and was **discarded as a
measurement artifact** (generation cost + unrealistically incompressible
depth). Kept here so the number doesn't resurface as evidence.

## Write sweep (120 s of data each, unpaced = max throughput)

| chunk | zstd | real-time factor | write MB/s | file/payload | writer CPU |
| --- | --- | --- | --- | --- | --- |
| 1 MiB | 0 | 6.14× | 205 | 1.0004 | ~1 core |
| 1 MiB | 3 | 5.11× | 158 | 0.927 | ~1 core |
| 4 MiB | 0 | 6.19× | 207 | 1.0001 | ~1 core |
| 4 MiB | 3 | 5.14× | 159 | 0.924 | ~1 core |
| 8 MiB | 0 | 6.08× | 203 | 1.0001 | ~1 core |
| 8 MiB | 3 | 5.08× | 157 | 0.923 | ~1 core |

- **≥2× real-time criterion: passed everywhere** (5.1–6.2×).
- 10-minute file (4 MiB / zstd-3): 5.17×, 18.5 GB, no degradation over
  the longer run.
- **Compression honesty:** overall ratio is only ~0.92 because device
  JPEG (~61% of bytes) is incompressible. Attributing all savings to
  depth: real dim-scene depth at 0.1 mm quantization compresses ≈ **1.24×**
  — far below discovery 08 §2's 2–3× desk estimate. The 0.1 mm low bits
  are sensor noise and cost compressibility; the estimate is corrected in
  08 §2. Storage math: ≈ **31 MB/s ≈ 112 GB/h** recorded. Keep-selects
  retention (≤50 GB) means roughly 25 minutes of keepers — consistent
  with the approval-round decision, and the review-and-delete workflow
  matters exactly as predicted.
- Writer CPU is ~1 core at *maximum* throughput; at real-time pace the
  duty cycle is ~1/5 of that. Note: zstd here also chews the JPEG bytes
  for ~0 gain; if recorder CPU ever matters, splitting color into
  uncompressed-chunk channels is the lever (MCAP compresses per chunk,
  and channels share chunks — a per-channel choice needs separate chunk
  streams or accepting the waste; measured waste today: ~2 s CPU per
  2-min take, acceptable).

## Seek (10-min file, 40 random timestamps, cold index)

p50 **5.8 ms**, p95 **20.1 ms**, max **28.0 ms** — comfortably under the
100 ms criterion.

## kill -9 (paced writes, 3 points)

| killed at | last fsync'd status | linear-scan recovered | loss bound |
| --- | --- | --- | --- |
| ~10 s | 8.20 s | **8.27 s** | < 1 s (status granularity) |
| ~35 s | 32.57 s | **33.10 s** | < 1 s |
| ~70 s | 67.20 s | **68.00 s** | < 1 s |

Recovery-by-linear-scan (index absent after kill) recovered *more* than
the last fsync'd sidecar status in all three runs — loss is bounded by
the tail chunk (~0.12 s of data at 4 MiB chunks), measured here to within
the 1 s status-write granularity. Criterion (≤ ~1 s): **passed**. (The Go
`mcap recover` CLI was not installed; recovery was exercised through the
C++ reader's fallback-scan path, which is what the replay layer will
actually use on damaged takes.)

## Disk-full (RLIMIT_FSIZE at 1 GB, SIGXFSZ ignored → write() = EFBIG)

- Prior chunks: **valid** — linear scan recovered 33.1 s cleanly up to
  the truncation point. ✅
- Writer behavior: **FAILED the criterion as-stocked** — mcap's default
  `FileWriter::handleWrite` runs `assert(written == size)` and aborts the
  process on a short write. No error status ever reaches the caller.
- **Binding consequence for phase 1:** the recorder implements its own
  `mcap::IWritable` that converts short writes/ENOSPC into an explicit
  recorder-failed state (take marked incomplete-with-journal, prior
  chunks intact, viewport untouched) — which discovery 08 §4 required
  anyway for the sidecar-journal design. E3 turns that from "good
  practice" into "mandatory".

## Chosen recording parameters (phase 1)

- Chunk size **4 MiB** (≈0.12 s of data → tail-chunk loss bound ~0.12 s;
  index granularity fine for scrubbing), **Zstd level 3** on mixed chunks
  (cheap enough; revisit per-channel split only if CPU becomes real),
  10-minute file rotation, sidecar journal fsync'd at 1 s.

## Environment

Same session/machine as E1 (see E1.md). btrfs `/home`, 505 GB free at
start; bench files deleted after measurement.
