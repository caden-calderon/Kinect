# E4 — Combined-Load Render Budget on the T550

**Status: PASSED — the Option N stack recommendation's second gate (with
E1) is met. Hypothesis grid point holds with >30% headroom; 1M particles
reachable with footprint LOD; memory far inside the 4 GiB ceiling; the
degradation ladder's first rung demonstrated live.**

Run 2026-07-29. Spike: `spikes/e4-render-budget/` (disposable; links the
real foundation library). GL 4.6 core on the T550 via PRIME offload
(Xwayland/GLX, `__NV_PRIME_RENDER_OFFLOAD=1`), driver 610.43.03.

## What ran (all in ONE process — combined load)

Replay of a real 20 s take (`takes/e4-input.mcap`, chair scene, dim/15 Hz
color) through the production capture path — MCAP read, JPEG decode,
FrameAssembler pairing — **plus** the production TakeRecorder writing to
the takes volume, **plus**: 217k observed points unprojected in the
vertex shader (E1 calibration), N particles (compute: curl+drag+integrate;
additive point draw), 4-level bloom chain, Reinhard+gamma composite, all
at 1920×1080 RGBA16F. 8 s per grid point (short runs per Caden).

Offscreen with per-frame fence sync: **presentation/compositor cost is
not in these numbers** (session possibly locked while AFK); the PRIME
present path gets verified visually with Caden at phase 3 acceptance.
Runs are windowless but the full GPU workload is identical.

GPU pass timings (timer queries, non-overlapping):

- observed points: 0.3 ms (fp2) → 0.9 (fp4) → 2.2 (fp8) — fill-rate
  scaling exactly as expected
- particle sim: 0.20/0.39/0.76 ms for 250k/500k/1M — compute is cheap
- particle draw: 1.3→13.5 ms (count × footprint² dominated; the real
  budget item, as discovery 02 §6 predicted)
- bloom chain: 0.5–0.65 ms — noise
- **color upload is the sleeper cost:** glTexSubImage2D of 1080p BGRX
  p50 2.4 ms, p95 5–7 ms (synchronous PCIe copy on the render thread).
  Phase 3 must use a PBO ring / persistent-mapped staging; this is the
  single biggest lever on p95.

Frame p95s are inflated relative to pass sums precisely by those upload
spikes — the p95 lands on frames where a fresh capture frame arrived.

## Memory + recorder under load

- VRAM: 462 MB used device-wide at peak grid point, **3.63 GiB free**
  (≥1 GiB criterion met with 3.6×).
- Full-process RSS high-water: **411 MB** (replay + decode + assembler +
  recorder + renderer in one process — stricter than the E4 setup, which
  allowed separate processes).
- Recorder wrote every submitted frame with **zero drops** through all
  nine grid points (`depth 2166/2166, color 1043/1043`).
- Discovery 06's ~4 GiB "looks comfortable" hypothesis: **validated**.

## Overload / degradation ladder

`shed` mode started at the worst grid point (fp8 + 1M, ~25 ms frames);
the auto-shed rule (p95 > 16.6 ms → halve footprint) stepped 8→4 at
frame 120 and 4→2 at frame 240, recovering to ~7 ms — the ladder's
"footprint LOD first" rung is enforceable and observable. Capture and
recording were untouched throughout, as the ladder requires.

## Verdict against the criteria

- 217k + ≥250k particles + bloom @60 Hz with ≥20% p95 headroom under
  combined load: **passed** (fp2 and fp4 at 250k; fp2 at 500k too).
- 1M particles reachable with footprint LOD: **yes** — fp2 + 1M runs
  60 Hz with 10% headroom; look authoring above 500k should prefer
  footprint ≤2 or 30 Hz.
- Memory high-waters leave ≥1 GiB VRAM: **passed** (3.6 GiB free).
- No structural failure; no API-shaped wall → **GL 4.6 confirmed, Option
  N stack recommendation now fully gated-in (E1 ✓ E4 ✓).**

## Caveats carried forward

- Presentation (PRIME offload copy to the iGPU-driven display +
  compositor) unmeasured — phase 3 exit gate covers it with Caden.
- Dim-scene take: color at 15 Hz halves upload frequency vs a lit scene;
  at 30 Hz color the upload spikes hit twice as many frames — another
  reason the PBO fix is phase-3 mandatory, and worth re-checking with a
  lit-room take.
